# 🌐 المعمارية الكاملة لنظام المزامنة السحابية لسيستمك (Sestamk Cloud Sync Master Architecture)

> **وثيقة الهندسة الشاملة لنظام المزامنة متعدد الأجهزة (Multi-Device Hybrid Cloud Sync)**  
> **الإصدار:** 2.0 (Post-Audit Edition)  
> **الهدف:** شرح وتوثيق دورة المزامنة من الألف إلى الياء، كشف وحل كافة الأخطاء الحسابية والأمنية والبرمجية، وتصميم واجهة المستخدم المتطورة مع قائمة الأجهزة وشريط التقدم الحي.

---

## 1. الهيكل العام ودورة حياة البيانات (End-to-End Data Flow)

يعتمد نظام سستمك على نموذج **(Offline-First Local + Distributed Hybrid Cloud)**:
1. كل جهاز كاشير يمتلك قاعدة بيانات محلية مستقلة **Microsoft SQL Server LocalDB** تضمن استمرارية البيع والطباعة بسرعة 0ms حتى في حال انقطاع الإنترنت نهائياً.
2. لكل منشأة/شركة قاعدة بيانات سحابية موزعة فائقة السرعة مبنية على **Turso (LibSQL Engine)** تُنشأ وتُدار برابط وتوكن مشفر خاص بالمنشأة فقط.
3. التغييرات تجري محلياً ⬅️ تسجلها تريجرات التتبع الذكية في جدول `_SyncLog` ⬅️ يدفعها محرك `SyncPushHandler` إلى السحابة ⬅️ يسحبها محرك `SyncPullHandler` إلى بقية أجهزة الكاشير والويتر لنفس الشركة.

```
┌────────────────────────────────────────────────────────────────────────┐
│                   جهاز الكاشير 1 (POS Device 1)                        │
│  [ إدخال فاتورة / صنف ] ──> [ SQL Server LocalDB ]                     │
│                                    │                                   │
│                        (تريجر التتبع TR_SyncTrack)                     │
│                                    ▼                                   │
│                           [ جدول _SyncLog ]                            │
│                                    │                                   │
│                        (محرك الدفع PushHandler)                        │
└────────────────────────────────────┼───────────────────────────────────┘
                                     │
                                     ▼ (HTTPS Hrana v2 Protocol)
┌────────────────────────────────────────────────────────────────────────┐
│              قاعدة بيانات المنشأة السحابية (Turso LibSQL Cloud)        │
│    • جداول المبيعات والأصناف والطاولات مع أعمدة sync_id و updated_at  │
│    • جدول أجهزة المنشأة [_SyncDevices] (لتتبع كل جهاز وآخر مزامنة له)  │
└────────────────────────────────────┬───────────────────────────────────┘
                                     │
                                     ▼ (HTTPS Hrana v2 Protocol)
┌────────────────────────────────────────────────────────────────────────┐
│                   جهاز الكاشير 2 / الويتر (POS Device 2)               │
│                        (محرك السحب PullHandler)                        │
│                                    │                                   │
│           (سحب التغييرات مع استثناء device_id ومعالجة الحذف)           │
│                                    ▼                                   │
│    [ تطبيق التغييرات محلياً مع تفعيل CONTEXT_INFO لمنع التكرار ]       │
└────────────────────────────────────────────────────────────────────────┘
```

## 2. نتائج التدقيق الشامل وقائمة الأخطاء المكتشفة والمعالجة (Audit Findings & Fixes)

### 🔴 الخطأ 1: إغراق سجل المزامنة بـ 10,829 سجلاً معلقاً لجدول الصلاحيات (Permissions Flood)
- **السبب:** جدول `Permissions` كان مدرجاً في `SyncableTableRegistry`، وتريجر التتبع كان يعمل في كل مرة تبدأ فيها الصيانة التلقائية لتحديث صلاحيات المستخدم، فيسجل آلاف السجلات غير الضرورية.
- **الحل:**
  1. حذف `Permissions` نهائياً من مصفوفة الجداول المزامنة.
  2. إسقاط تريجر `TR_Permissions_SyncTrack` نهائياً.
  3. تنظيف وحذف سجلات `Permissions` القديمة تلقائياً من `_SyncLog`.

### 🔴 الخطأ 2: تسريب موارد `SqlCommand` في محرك السحب (`SyncPullHandler`)
- **السبب:** كان يتم إنشاء `updateCmd` و `insertCmd` كأوامر جديدة دون تغليفها بكتل `Using`، مما يسبب تسريباً لمقابض الاتصال وموارد الذاكرة مع كل دورة مزامنة.
- **الحل:** تغليف كافة أوامر `SqlCommand` داخل كتل `Using` صريحة لضمان التحرير الفوري للموارد بعد انتهاء التنفيذ.

### 🔴 الخطأ 3: غياب فلترة الجهاز في أول سحب (First Pull Echo / Duplication)
- **السبب:** عند أول سحب للجدول (`LastPullAt Is Nothing`)، كان الاستعلام ينفذ: `SELECT * FROM [table] WHERE is_deleted = 0` دون استثناء `device_id <> myDeviceId`، مما يسحب التغييرات التي قام الجهاز نفسه برفعها للتو ويعيد إدراجها محلياً.
- **الحل:** إضافة شرط `(device_id IS NULL OR device_id <> ?)` في كافة حالات السحب (الأولية والدورية).

### 🔴 الخطأ 4: عدم معالجة الحذف في السحب (Soft-Delete Handling on Pull)
- **السبب:** في السحب الدوري، عندما يقوم جهاز آخر بحذف صف منطقياً في السحابة (`is_deleted = 1`)، كان محرك السحب يقرأ الصف ويعيد إدراجه أو تحديثه محلياً كصف عادي نشط بدلاً من حذفه!
- **الحل:** فحص عمود `is_deleted` في الصف القادم من السحابة؛ إذا كان `1`، يتم تنفيذ حذف منطقي أو حذف حقيقي محلياً `DELETE FROM [table] WHERE sync_id = @sid` أو تحديث `is_deleted = 1`.

### 🔴 الخطأ 5: مشكلة فقدان السجلات عند تجاوز 500 صف (Pagination Gap in Pull)
- **السبب:** كان الاستعلام يجلب أول 500 صف فقط، ويحدّث تاريخ آخر سحب إلى وقت الخادم الحالي `SYSUTCDATETIME()`. إذا كان هناك 600 صف معدل، تضيع الـ 100 صف المتبقية للأبد لأن التاريخ تقدم عنها!
- **الحل:**
  1. تنفيذ حلقة تكرارية (Loop) تستمر في السحب حتى ينتهي الجدول ويكون عدد الصفوف العائدة أقل من الـ Limit.
  2. تحديث `LastPullAt` إلى `MAX(updated_at)` الفعلي من الصفوف المسحوبة، وليس وقت الجهاز المحلي لتفادي مشاكل فروق التوقيت (Clock Skew).

### 🔴 الخطأ 6: رفع دفعة واحدة فقط وتوقف المحرك (Single Batch Push Limitation)
- **السبب:** كان `SyncPushHandler` يقرأ أول 50 سجلاً فقط وينتهي، فإذا كان هناك 1000 حركة معلقة، يحتاج النظام إلى 20 دورة كاملة للانتهاء منها!
- **الحل:** تنفيذ حلقة دفع ذكية (Batch Loop) تستمر في سحب ودفع دفعات الـ 50 حتى ينتهي السجل بالكامل ويصل عدد الحركات المعلقة إلى 0.

### 🔴 الخطأ 7: تأمين توكن المنصة وحماية الحساب المشترك
- **السبب:** وجود توكن المنصة الثابت في الكود يمثل خطراً أمنياً إذا تم فك تجميع الملف.
- **الحل:** عزل صلاحيات الوصول واستخدام توكنات الترخيص المعتمدة الصادرة عبر Supabase لكل منشأة على حدة، وتخزينها بتشفير DPAPI محلياً.

## 3. معمارية تتبع أجهزة المنشأة ومراقبة آخر ظهور (`_SyncDevices`)

لتلبية متطلب معرفة **"جميع الأجهزة داخل نفس الشركة وكل جهاز آخر مرة عمل مزامنة إمتى"**:
تم إنشاء وتوثيق جدول موحد على قاعدة البيانات السحابية Turso للمنشأة باسم `_SyncDevices`:

```sql
CREATE TABLE IF NOT EXISTS [_SyncDevices] (
    [device_id] TEXT PRIMARY KEY,
    [device_name] TEXT NOT NULL,
    [app_version] TEXT,
    [os_info] TEXT,
    [first_seen_utc] TEXT,
    [last_sync_utc] TEXT NOT NULL,
    [last_push_utc] TEXT,
    [last_pull_utc] TEXT,
    [total_pushed] INTEGER DEFAULT 0,
    [total_pulled] INTEGER DEFAULT 0,
    [is_active] INTEGER DEFAULT 1
);
```

### كيف يتفاعل كل جهاز مع الجدول؟
1. عند بدء كل دورة مزامنة (Push أو Pull):
   - يرسل الجهاز جملة `INSERT OR REPLACE INTO [_SyncDevices]` تتضمن:
     - `device_id`: معرّف الجهاز الفريد.
     - `device_name`: اسم الجهاز (مثلاً: "كاشير 1 - الصالة").
     - `app_version`: إصدار البرنامج (v1.4.2).
     - `last_sync_utc`: التوقيت اللحظي للمزامنة.
     - العدادات التراكمية.
2. في شاشة إعدادات المزامنة (`UCCloudSyncSettings`):
   - يتم استعلام جدول `_SyncDevices` وعرض جدول بطاقات متطور للأجهزة:
     - اسم الجهاز ونوعه (🖥️ كاشير رئيسي / 📱 ويتر متنقل).
     - الإصدار ونظام التشغيل.
     - وقت وتاريخ آخر مزامنة ناجحة (منذ دقيقتين، اليوم 02:30 م...).
     - بادج الحالة: `🟢 متصل ونشط` أو `⚪ غير متصل منذ فترة`.

## 4. تصميم الواجهة الرسومية الجديدة وتجربة المستخدم (UI/UX Transformation)

### المكونات البصرية الجديدة في `UCCloudSyncSettings`:
1. **شريط تقدم المزامنة الحي (`Guna2ProgressBar`):**
   - يظهر بسلاسة عند الضغط على "مزامنة الآن" أو عند عمل المزامنة التلقائية.
   - يعرض النسبة المئوية الدقيقة (0% ⬅️ 100%) مع نص توضيحي متحرك:  
     *«جاري رفع التغييرات المحلية... (25 من 25)»*  
     *«جاري سحب التغييرات من السحابة... (جدول المبيعات)»*
2. **بطاقات المؤشرات الإحصائية (Stats Bento Grid):**
   - بطاقة حالة الربط السحابي (`🟢 مفعّل وجاهز`).
   - بطاقة آخر مزامنة ناجحة (`🕒 اليوم 03:15 م`).
   - بطاقة التغييرات المعلقة محلياً (`📦 0 تغيير معلق`).
3. **قائمة أجهزة المنشأة في نفس الشركة (Company Devices Panel):**
   - جدول أو بطاقات تعرض كافة الأجهزة المتصلة بنفس الحساب السحابي.
   - إظهار الجهاز الحالي ببادج تمييز `(هذا الجهاز ⭐)`.
   - إظهار توقيت آخر اتصال لكل جهاز بدقة.
4. **سجل حركات المزامنة (Live Activity Log):**
   - جدول تفاعلي مترجم مع إيموجي للعمليات (`➕ إضافة`, `✏️ تعديل`, `❌ حذف`).
   - بادجات حالة واضحة (`✅ تم`, `⏳ معلق`).
   - زر مسح السجل بتأكيد أمني.
